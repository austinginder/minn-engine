# WP-CLI on the engine

The `wp` binary itself runs unchanged (WP-CLI is MIT). `public/wp-cli.yml` requires
`minn/cli.php`, which registers the engine's verbs for WP-CLI's `before_wp_load`
phase. WP-CLI runs that phase before it looks for a WordPress install, so the verbs
below work on a webroot with no `wp-load.php` and no `wp-includes/`; anything else
still fails with WP-CLI's own "This does not seem to be a WordPress installation".
Code: `public/minn/src/Minn/Cli/`. Suite: `tests/cli.test.php` runs every verb
against the engine's webroot and the parked reference on the same database and
compares stdout and the exit code.

## How the override works

WP-CLI loads `require:` files before it registers its bundled commands. A leaf
registered under a parent that does not exist yet (`option get` before `option`) is
deferred, added after the bundle, and replaces the bundle's leaf of the same name.
`@when before_wp_load` on the method (and `when` in the registration) puts the verb in
the early phase. WP-CLI also registers `plugin` as a command namespace before the
class command; the namespace would otherwise keep WP-CLI's `list` (whose constructor
requires `wp-admin/includes/plugin.php`). Each leaf is re-added on
`after_add_command:{parent}` so the engine's list is the one that stays. The command boots the engine on first use (`Minn\Cli\Runtime`):
it requires the site's `wp-config.php`, whose trailing `wp-settings.php` require
reaches `minn/bootstrap.php`, which under WP-CLI only registers the autoloader.
`$table_prefix` is copied to the global the engine reads.

## Verbs

| Verb | Behaviour matched |
|---|---|
| `option get <key> [--format=var_export\|json\|yaml]` | Missing key: `Error: Could not get 'x' option. Does it exist?` (exit 1). Serialized values decode through the engine's own reader (`Serialized::decode`: scalars and arrays, objects refused) and print through WP-CLI's formatter, so `sticky_posts` reads `array (\n  0 => 5,\n)` and `[5]` as JSON; a plain string stays a string (`posts_per_page --format=json` is `"10"`). |
| `option add <key> [<value>] [--format] [--autoload]` | `Success: Added 'x' option.`; existing key: `Error: Could not add option 'x'. Does it already exist?`. Stored with `autoload = on`. |
| `option update <key> [<value>] [--format] [--autoload]` | Value from the argument or STDIN; `--format=json` decodes. Same value: `Success: Value passed for 'x' option is unchanged.`; otherwise `Success: Updated 'x' option.`. A key that did not exist is inserted with `autoload = auto`. Arrays are stored serialized. |
| `option delete <key>...` | `Success: Deleted 'x' option.` per key; a missing key is a `Warning: Could not delete 'x' option. Does it exist?` and the exit code stays 0. |
| `user list [--role] [--field] [--fields] [--format]` | Ordered by `user_login`; fields `ID,user_login,display_name,user_email,user_registered,roles`; `roles` joined with `,`; `ids` and `count` formats; `--role` filters. Only roles registered in `wp_user_roles` count (a plugin-granted role the registry does not know is not listed, as on the reference). |
| `user get <id\|email\|login> [--field] [--fields] [--format]` | Record order `ID,user_login,user_email,user_registered,display_name,roles`, `ID` as the stored string, roles joined with `, `. Unknown: `Error: Invalid user ID, email or login: 'x'`. |
| `user login <id\|email\|login>` | Prints `{siteurl}/wp-login.php?user_id=N&cove_login_token=T` (7 hex chars) after storing the token's sha256 in `cove_login_token` and the mint time in `cove_login_token_time`: the contract of the captaincore helper mu-plugin, which the engine honours natively at `wp-login.php` (valid for fifteen minutes, spent on use, 302 to `/wp-admin/` with a fourteen-day session; any failure is the same 403 so ids cannot be probed, and failures count toward the sign-in throttle). Unknown: `Error: User not found: x`. |
| `user create <login> <email> [--role] [--user_pass] [--first_name] [--last_name] [--display_name] [--send-email] [--porcelain]` | Writes a real `$wp$2y$10$` hash and the 14 default meta rows. Duplicate login: `Error: The 'x' username is already registered.`; duplicate email: `Error: Sorry, that email address is already used!`; unknown role: `Error: Role doesn't exist: x`. No `--user_pass` prints a generated `Password:` line. `--porcelain` prints only the id. First+last names become the display name when `--display_name` is omitted. `--send-email` sends the engine's password-reset mail. |
| `user update <user> [--display_name] [--user_email] [--user_pass] [--role] [--first_name] [--last_name]` | Unknown: `Warning: Invalid user ID, email or login: 'x'` then `Error: No valid users found.` Success: `Updated user N.` |
| `user delete <user> [--reassign=<id>] [--yes]` | `--reassign` moves posts; without it the user's posts are deleted. Success: `Removed user N from {home}.` |
| `cache flush` | No object cache: `Success: The cache was flushed.` so fleet scripts that call it after a write do not abort. |
| `cron event list [--hook] [--due-now] [--field] [--fields] [--format]` | Every scheduled event from the `cron` option, columns `hook, next_run_gmt, next_run_relative, recurrence` (a recurring event's recurrence is its interval as two whole units, e.g. `12 hours`; a single event is `Non-repeating`). `--hook` filters, `--due-now` keeps events at or before now, `ids`/`count` reduce to hooks. Every verb boots the full runtime first, so a plugin's schedules and callbacks are registered. |
| `cron event run [<hook>...] [--due-now] [--all]` | Runs the selected events: a named hook (each instance), `--due-now` (ready events), or `--all`. Recurring events are rescheduled, single events removed, then the hook fires. `Executed the cron event 'x' in Ns.` per event, then `Success: Executed a total of N cron event(s).` No selector: `Error: Please specify one or more cron events, or use --due-now/--all.` (exit 1). An unknown named hook: `Error: Invalid cron event 'x'` (exit 1, before any run). Ignores the run lock, as the reference does. |
| `cron event schedule <hook> [<next-run>] [<recurrence>] [--<field>=<value>]` | `next-run` defaults to `now` and is parsed by `strtotime`; a recurrence must be a registered schedule. Success: `Success: Scheduled event with hook 'x' for <Y-m-d H:i:s> GMT.` A duplicate within the ten-minute window: `Error: Event not scheduled.` Bad datetime / unknown recurrence / extra positionals each their own error (exit 1). Event args passed as `--field=value` warn `Numeric keys should be used for the hook arguments.` |
| `cron event delete <hook>...` | Removes every instance of each hook: `Success: Deleted a total of N cron event(s).` An unknown hook: `Error: Invalid cron event 'x'` (exit 1). |
| `cron event unschedule <hook>` | Removes every instance of one hook: `Success: Unscheduled N event(s) for hook 'x'.` None scheduled: `Error: No events found for hook 'x'.` (exit 1). |
| `cron schedule list [--field] [--fields] [--format]` | The registered schedules (`cron_schedules` plus core's), columns `name, display, interval`, sorted by interval. |
| `cron test` | `Success: WP-Cron spawning is working as expected.`, or a `DISABLE_WP_CRON` warning when the constant is set. |
| `option set` | Alias of `option update`. |
| `search-replace <old> <new> [<table>...] [--dry-run] [--all-tables] [--report-changed-only]` | Walks string columns (skips `guid` and numeric types), including serialized-PHP arrays of scalars without unserialize. Report columns Table/Column/Replacements/Type (PHP). Identical strings: `Warning: Replacement value 'x' is identical to search value 'x'. Skipping operation.` CaptainCore's https/launch/migrate scripts pass `--all-tables --report-changed-only`. |
| `wp minn version`, `wp minn info` | The engine's own identity. |
| `plugin list [--status] [--field] [--fields] [--format]` | Installed plugins from disk plus must-use and drop-ins, in that order, each group sorted by name. `name` is the directory (or the drop-in filename); `title` and `version` come from the file headers; `status` is `active` / `inactive` / `must-use` / `dropin`. Drop-ins keep an empty version (the reference does too). `update` is `none` for regular plugins and `false` for must-use and drop-ins: the engine does not call the wordpress.org update API. CaptainCore's `fetch-site-data` reads `--format=json --fields=name,title,status,version`. |
| `theme list [--status] [--field] [--fields] [--format]` | Themes from `style.css` headers, sorted by name. The stylesheet is `active`; its parent (when different) is `parent`; the rest are `inactive`. |
| `theme install <theme\|zip\|url>... [--version] [--force] [--activate]` | wordpress.org slug, a local zip, or a zip URL. Unknown slug: `Warning: x: Theme not found` plus `Warning: The 'x' theme could not be found.` then `Error: No themes installed.` Already on disk: `Warning: x: Theme already installed.` and `Success: Theme already installed.` (exit 0), or `Success: Installed N of M themes.` when at least one was new. `--activate` switches even when the theme was already installed. `--force` overwrites and prints `Theme updated successfully.` The engine does not use WP-CLI's download cache, so it never prints `Using cached file`. `--insecure` and `--ignore-requirements` are ignored. |
| `theme activate <theme>` | Missing: `Error: The 'x' theme could not be found.` Already active: `Warning: The '{Theme Name}' theme is already active.` (the style.css name, not the folder). Success: `Success: Switched to '{Theme Name}' theme.` Writes `stylesheet`, `template` (parent folder, or itself), and `current_theme`. |
| `theme delete <theme>... [--force]` | Missing: `Warning: The 'x' theme could not be found.` then `Success: Theme already deleted.` Active theme without `--force`: `Warning: Can't delete the currently active theme: {slug}` then `Error: No themes deleted.` Success: `Deleted 'x' theme.` plus `Success: Deleted N of M themes.` |
| `theme is-installed <theme>` | Exit 0 if `wp-content/themes/<slug>/` exists, else 1. No output. |
| `theme is-active <theme>` | Exit 0 if `stylesheet` is that folder, else 1. No output. A missing theme is not active. |
| `theme search <search> [--page] [--per-page] [--field] [--fields] [--format]` | wordpress.org query. Default table is `name, slug, rating`. Table/yaml print `Success: Showing N of T themes.` before the rows. json/csv/count print only the Formatter output (`count` is this page's rows, not T). Zero hits: `Showing 0 of 0 themes.` plus the header. |
| `theme update [<theme>...] [--all] [--exclude] [--minor] [--patch] [--format] [--version] [--dry-run]` | Alias `upgrade`. No args: `Error: Please specify one or more themes, or use --all.` Missing: `Error: The 'x' theme could not be found.` (fatal, stops). `--all` with nothing: `Success: Theme already updated.` `--all --dry-run` with nothing: `No theme updates available.` Named current: `Success: Theme already updated.` An offer prints `Downloading update from {zip}...` / `Unpacking the update...` / `Installing the latest version...` / `Removing the old version of the theme...` / `Theme updated successfully.` then a table of `name, old_version, new_version, status=Updated` and `Success: Updated N of M themes.` `--format=json`/`csv` print only the rows (empty stdout when nothing changed; no Success line). `--format=summary` uses the style.css name (`Twenty Sixteen updated successfully from version 3.8 to version 3.9`). `--dry-run` table is `Available theme updates:` plus `name, status, version, update_version`. `--exclude` always prints `Skipped updates for: …` in table/summary, even when the list is empty (`--exclude=`). `--minor` keeps the same major; `--patch` keeps major.minor. `--version` force-installs that release using the install wording. `--insecure` is ignored. The engine does not print `Using cached file` or maintenance-mode lines. |
| `plugin install <plugin\|zip\|url>... [--version] [--force] [--activate]` | wordpress.org slug, a local zip, or a zip URL. Unknown slug: `Warning: x: Plugin not found.` plus `Warning: The 'x' plugin could not be found.` then `Error: No plugins installed.` Already on disk: `Warning: x: Plugin already installed.` and `Success: Plugin already installed.` (exit 0). New copies: `Success: Installed N of M plugins.` Partial (some missing): `Error: Only installed N of M plugins.` (exit 1). `--activate` prints `Activating 'x'...` then `Plugin 'x' activated.` even when the plugin was already on disk. `--force` overwrites and prints `Plugin updated successfully.` A folder that exists is treated as already installed (the engine checks the disk first). The engine does not use WP-CLI's download cache. `--insecure`, `--ignore-requirements`, and `--activate-network` are ignored. |
| `plugin delete <plugin>...` | Removes the folder (or a single-file `slug.php`). Missing: `Warning: The 'x' plugin could not be found.` then `Success: Plugin already deleted.` Success: `Deleted 'x' plugin.` plus `Success: Deleted N of M plugins.` Does not deactivate first. A symlink is unlinked; the target is not walked. |
| `plugin is-installed <plugin>` | Exit 0 if `wp-content/plugins/<slug>/` or `wp-content/plugins/<slug>.php` exists, else 1. No output. |
| `plugin is-active <plugin> [--network]` | Exit 0 if the plugin is in `active_plugins` (or a pure extension in `minn_active_extensions`), else 1. Missing is not active. `--network` is ignored. |
| `plugin search <search> [--page] [--per-page] [--field] [--fields] [--format]` | wordpress.org query. Same default table and Success-before-rows rule as theme search, with "plugins". Names keep directory HTML entities (`&amp;`). |
| `plugin update [<plugin>...] [--all] [--exclude] [--minor] [--patch] [--format] [--version] [--dry-run]` | Alias `upgrade`. No args: `Error: Please specify one or more plugins, or use --all.` Missing: `Warning: The 'x' plugin could not be found.` then `Error: No plugins updated (N failed).` (named current plugins are silent; a mix of missing and current is still that error). `--all` with nothing: `Success: Plugin already updated.` `--all --dry-run` with nothing: `No plugin updates available.` An offer uses the same progress lines as theme update (`… of the plugin…` / `Plugin updated successfully.`) then `Success: Updated N of M plugins.` Partial: `Error: Only updated N of M plugins (K failed).` `--format=json`/`csv` print only the rows. `--format=summary` uses the plugin header name (`Hello Dolly update from version 1.6 to version 1.7.2` on dry-run). `--exclude` prints `Skipped updates for: …` in table/summary, including an empty `--exclude=`. `--minor`/`--patch` as for themes. `--version` force-installs that release using the install wording; a missing plugin is only a warning (exit 0). `--insecure` is ignored. The engine does not print `Using cached file` or maintenance-mode lines. |
| `plugin activate|deactivate <plugin>...` | The reference's wording line for line (`Plugin 'x' activated.`, `Success: Activated 1 of 1 plugins.`, `Warning: The 'x' plugin could not be found.` + `Error: No plugins activated.`, `Warning: Plugin 'x' is already active.` + `Success: Plugin already activated.`). A WordPress plugin joins or leaves the sorted `active_plugins` list (its stored state; the engine runs none of its code); a Minn extension joins or leaves `minn_active_extensions`, and deactivating one releases the plugin files it stood in for. `Content\PluginState` is shared with `PUT wp/v2/plugins`. Deactivating `minn-admin` switches the admin off (contracts/minn-admin.md). |
| `rewrite flush [--hard]` | `Success: Rewrite rules flushed.` The engine resolves URLs from options; `--hard` does not write `.htaccess`. |
| `rewrite structure <permastruct> [--category-base] [--tag-base] [--hard]` | Writes `permalink_structure` (and the optional bases), then `Success: Rewrite structure set.` plus `Success: Rewrite rules flushed.` |
| `maintenance-mode activate\|deactivate\|status\|is-active` | Writes or removes `{ABSPATH}/.maintenance`. Activate: `Enabling Maintenance mode...` then `Success: Activated Maintenance mode.` Already on: `Error: Maintenance mode already activated.` Deactivate mirrors that (`Disabling` / `Deactivated` / already deactivated). Status: `Maintenance mode is active.` or `… is not active.` `is-active` is exit 0/1 with no output. The public site stays up while the file is present; fleet scripts bookend updates with these verbs. |
| `wp minn probe` | `key:value` lines for `engine`, `engine_version`, `core`, `home_url`, `php_version`, `plugins`, `themes`, `mu_plugins`. JSON values have no newlines; split on the first colon. This is the engine-native stand-in for the inventory `fetch-site-data` currently gathers via `wp plugin list` / `wp theme list` / `wp core version` inside WordPress. |

## Not yet

- `wp db …` and `wp config …` are WP-CLI's own and read `wp-config.php` directly.
- `wp core update` and `wp core verify-checksums` wait until Minn has a release
  of its own. They become the engine's updater and integrity check, not a
  rewrite of WordPress core commands. Until then the bundle's copies refuse
  because they need WordPress.
- `post` is absent; the list grows from what the fleet actually invokes.
- `wp language core/plugin/theme update` is still the bundle. CaptainCore's update script calls them after plugin/theme update; they wait on a language-pack reader.
- `option get` of an option holding a serialized object prints the raw blob.
